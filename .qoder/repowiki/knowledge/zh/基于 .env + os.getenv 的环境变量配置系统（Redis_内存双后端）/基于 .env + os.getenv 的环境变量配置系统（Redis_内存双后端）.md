## 1. 采用的方案

项目没有使用任何配置框架（如 pydantic-settings、dynaconf、pyyaml），而是采用最朴素的 **`.env` + `os.getenv()`** 模式：
- 在 `rag_langchain.py` 模块导入时调用 `load_dotenv()`（第 50 行），从同目录的 `.env` 文件加载键值对到进程环境变量。
- 所有运行时参数通过 `os.getenv("KEY", default)` 读取，默认值直接写在代码里。
- 缓存层在 `cache.py` 中集中定义一组与缓存相关的配置常量，同样走 `os.getenv`。

## 2. 关键文件

| 文件 | 职责 |
|---|---|
| `rag_langchain.py` | RAG 管道入口，`load_dotenv()` 在此触发；承载模型路径、检索参数、切块参数等配置 |
| `cache.py` | 缓存后端选择、TTL、版本号、统计等配置集中地 |
| `app.py` | FastAPI 应用入口，仅消费上层暴露的常量，不直接读 env |
| `tools/mini_redis_resp.py` / `tools/resp_client.py` | 测试用极简 RESP 客户端，配合 `RESP_CLIENT_MODULE` 环境变量替换 redis-py |
| `verify_cache.py` / `verify_redis_backend.py` | 验证脚本，通过 `VERIFY_LOG`、`RESP_CLIENT_MODULE` 等 env 控制行为 |

## 3. 架构与约定

### 3.1 配置来源分层

所有配置都来自同一来源——进程环境变量，由 `.env` 注入。不存在配置文件（yaml/toml/ini）、命令行参数或数据库配置表。

### 3.2 配置项清单与默认值

**RAG 管道（`rag_langchain.py`）**

| 环境变量 | 默认值 | 含义 |
|---|---:|---|
| `BGE_QUERY_PREFIX` | `Represent this sentence for searching relevant passages: ` | bge 英文检索 query 前缀 |
| `CHUNK_TOKENS` | `256` | 按 token 切块的块大小 |
| `CHUNK_OVERLAP_TOKENS` | `40` | 重叠 token 数 |
| `SEMANTIC_CACHE` | `"0"` | 语义缓存开关（必须为 `"1"` 才启用） |
| `SEMANTIC_THRESHOLD` | `0.95` | 语义缓存余弦相似度阈值 |

此外还有硬编码但可被覆盖的常量：`LANG_MODELS`、`LANG_MAX_SEQ`、`LANG_COLLECTIONS`、`DEFAULT_LANG`、`RETRIEVE_K=20`、`RERANK_TOP_N=5`、`RERANK_MODEL`、`CHROMA_DB_PATH`、`DEFAULT_SOURCE="doc.pdf"`。

**缓存层（`cache.py`）**

| 环境变量 | 默认值 | 含义 |
|---|---:|---|
| `REDIS_URL` | `redis://127.0.0.1:6379/0` | Redis 连接 URL |
| `CACHE_BACKEND` | `auto` | 后端选择：`auto` / `redis` / `memory` |
| `CACHE_ANSWER_TTL` | `3600` | 问答结果 TTL（秒） |
| `CACHE_EMBEDDING_TTL` | `86400` | 向量缓存 TTL（秒） |
| `CACHE_RERANK_TTL` | `3600` | 精排分数 TTL（秒） |
| `RESP_CLIENT_MODULE` | `redis` | 测试钩子：用自定义模块替换 redis-py |

### 3.3 后端自动降级策略

`_get_backend()`（`cache.py` 第 176 行）实现三级逻辑：
1. `CACHE_BACKEND == "memory"` → 直接使用 `_MemoryBackend`（进程内 dict + RLock）。
2. 否则尝试连接 Redis（`_connect_redis()`），成功则返回 `_RedisBackend`。
3. 如果连接失败且 `CACHE_BACKEND != "redis"`（即 auto 模式），**静默降级**到 `_MemoryBackend` 并打印日志；若显式设为 `redis` 则抛出 `RuntimeError`。

降级后的行为差异：
- memory 后端是单进程的，多实例之间不共享缓存。
- Redis 后端通过 `VERSION_KEY = "rag:cache_version"` 做跨进程版本失效。
- 两种后端都实现了统一的 `get/set/delete_prefix/incr/ping` 接口。

### 3.4 Key 命名规范

缓存 key 统一遵循以下格式：
- 通用 key：`rag:v{version}:{kind}:{sha256[:32]}`（`make_key` 函数）
- embedding key：`rag:embed:{model_tag}:{text_hash}`（含模型标签，避免中英两个模型互相覆盖）
- rerank key：`rag:rerank:{sha256(question||doc)}`

版本号通过 `bump_version()` 原子递增，上传文档后旧答案立即失效。

### 3.5 懒加载与线程安全

所有重型资源（embedding 模型、Chroma client、cross-encoder、tokenizer、缓存后端）均采用 **双检锁（double-checked locking）** 懒加载，并用 `threading.Lock` / `RLock` 保护，因为 FastAPI 会把同步端点丢进线程池。

## 4. 约定与约束

- **所有配置都通过 `os.getenv` 读取**，没有配置文件解析器、schema 校验或类型转换中间件。
- **`.env` 只在 `rag_langchain.py` 导入时加载一次**（`load_dotenv()`），后续修改不会热更新。
- **缓存后端默认 `auto`**：生产环境应显式设置 `CACHE_BACKEND=redis`，否则 Redis 不可用时会静默降级为内存后端，导致多进程缓存不共享。
- **缓存异常一律 fail-open**：`get()` 捕获所有异常返回 `None`，`set()` 捕获异常直接 pass，保证“缓存丢了只变慢，不会变错”。
- **不同 embedding 模型的向量必须分 key 存储**（`model_tag` 拼入 key），这是代码注释反复强调的硬性约束，避免两个语种模型互相覆盖向量。
- **知识库变更后必须调用 `bump_version()`**：版本号参与所有 QA/rerank key 计算，使旧缓存立即失效。
- **collection 名有 Chroma 硬性约束**：3~512 字符、仅 `[a-zA-Z0-9._-]`、首尾字母数字，所以本项目用 `rag_zh` / `rag_en` 而非 `zh` / `en`。
- **`CHROMA_DB_PATH` 必须用绝对路径**：chromadb 的 `SharedSystemClient` 按路径字符串注册进程内实例，相对路径写法会导致同一目录出现多个 SQLite 连接和数据不一致。
- **Redis 连接强制走 RESP2**：`protocol=2`，兼容 Redis 6 以下版本（不含 HELLO 命令）。
- **清理缓存时使用 `SCAN` 而非 `KEYS`**：避免阻塞整个 Redis 实例。

## 5. 未覆盖的配置场景

- 没有 feature flag 机制（语义缓存开关是最接近的布尔开关）。
- 没有 secrets 管理（DeepSeek API key 等凭据未在代码中出现，可能通过 ChatDeepSeek 默认方式获取）。
- 没有配置文件的 schema 校验或类型检查。
- 没有配置热重载。
- 没有区分 dev/staging/prod 等多套配置集。
