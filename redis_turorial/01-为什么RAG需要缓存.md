# 01 为什么 RAG 需要缓存

## 一次问答到底在烧什么

RAG 的一次提问要串行做四件重活（对应 `rag_langchain.py` 的管道）：

| 环节 | 成本 | 能复用吗 |
|---|---|---|
| 问题向量化 | 模型前向一次，几十毫秒 | ✅ 同一个问题完全可复用 |
| 向量召回 | Chroma 查一次 | ✅ 结果是确定的，可复用 |
| Cross-Encoder 精排 | **召回 20 条就要前向 20 次**，本地 CPU 上百毫秒 | ✅ (问题, 片段) 组合可复用 |
| DeepSeek 生成 | **5~15 秒**，且**按 token 计费** | ✅ 同一问题答案可复用 |

前三个环节烧的是**算力**，最后一个是**钱 + 时间**。

而真实使用中：用户重复提问、多人问同一个问题、刷新页面重问——**这些请求全部在重算一模一样的东西**。

## 关键区分：模型单例 ≠ 缓存

这是最容易被混淆的一点。项目里两个东西长得很像，但解决的是不同问题：

| | 模型单例 | 缓存 |
|---|---|---|
| 解决什么 | 同一进程内不重复**加载模型** | 同一输入不重复**计算结果** |
| 项目里在哪 | `_get_cross_encoder()` 懒加载 | `cache.py` 全套 |
| 丢掉会怎样 | 变慢（重新加载 1GB 模型） | 变慢（重算一遍），**不会变错** |
| 跨进程 | 每个进程各一份 | Redis 下全局共享 |

**模型单例只保证模型加载一次，但每次请求的文本仍然要完整走一遍前向计算。**
缓存才是连计算都省掉。

## 三条铁律

这三点贯穿整个 `cache.py` 的设计，读代码时你会反复看到它们的影子。

### 铁律一：缓存是加速层，不是数据源

> 清掉缓存后重新提问，答案应该**完全一致**。

推论：**任何缓存异常都直接回落真实计算**。项目里所有的读写都包了 try/except：

```python
def get(key: str) -> Optional[Any]:
    try:
        return _loads(_get_backend().get(key))
    except Exception:
        return None        # fail-open：读失败当作未命中，走真实计算

def set(key: str, value: Any, ttl: int) -> None:
    try:
        _get_backend().set(key, _dumps(value), ttl)
    except Exception:
        pass               # fail-open：写失败不影响返回结果
```

这个模式叫 **fail-open**——出问题时"放行"到正常路径，而不是"拦下"报错。

### 铁律二：失效比写入难

写入错了，只是没缓存上，用户无感。

**失效错了，用户会拿到一个"看起来很正常、但基于旧文档"的答案。**
在 RAG 场景下这比"慢几秒"严重得多——用户无法察觉自己在读错误信息。

所以项目在"知识库变了"这件事上做得特别重（见第 5 节）。

### 铁律三：缓存不能成为单点依赖

> 缓存挂了，系统应该只是变慢，而不是整个不可用。

这就是为什么项目有 `memory` 降级后端（见第 4 节），而不是"连不上 Redis 就报错"。

## 本项目实测的收益

`/cache/stats` 接口能看到实时数据：

```bash
curl http://127.0.0.1:8000/cache/stats
```

关注 `asked_pipeline_saved` 这个字段——它等于 QA 缓存命中次数，
也就是**省下的 DeepSeek 调用次数**。每一次都意味着省了 5~15 秒和一笔 token 费用。

## 一个反直觉的点：什么时候不该用缓存

看 `rag_langchain.py` 里语义缓存的注释：

> 阈值调高（0.95+）收益有限，调低（0.85）会误命中、答非所问，
> 而 RAG 场景下"答错"比"慢一点"严重得多

**近似匹配天然有误判风险**，所以项目的语义缓存默认**关闭**（`SEMANTIC_CACHE=0`）。
这是一个成熟的设计判断：**一个收益不确定、但有概率让答案变错的功能，默认不应该开。**
