# 02 三层缓存设计

对应代码：`cache.py` 全文。三层各自独立，任意一层命中都能省掉对应环节。

```
用户提问
   │
   ├─① 问答缓存（问题原文 + 检索参数 + 语种 + 缓存版本  →  答案 + 引用片段）
   │      命中 ──► 直接返回（不查库、不精排、不调 DeepSeek）
   │      未命中
   ▼
   ② 向量缓存（文本 → 向量）──► 只把未命中的文本送进 embedding 模型
   ▼
   ③ 精排分数缓存（(问题,片段) → 分数）──► 只对未算过的组合跑 cross-encoder
   ▼
   DeepSeek 生成  ──►  回写 ①
```

## ① 问答缓存 —— 省时间、省钱

```python
def get_answer(question, top_n, k, lang=""):
    key = make_key("qa", lang, question.strip(), str(k), str(top_n))
```

最终 key 形如：

```
rag:v3:qa:8f2a1c...        # 32 位十六进制摘要
```

**Value**：`{"answer": ..., "sources": [...], "ts": ..., "question": ...}`
**TTL**：`CACHE_ANSWER_TTL`，默认 3600 秒（1 小时）

### 三个设计决定，每个都有理由

**为什么问题要 `.strip()`？**
避免"末尾多打一个空格就当成新问题"，导致缓存命中率莫名其妙地低。

**为什么检索参数 `k` / `top_n` 要进 key？**
改参数后必须拿到新口径的结果。如果不进 key，你调了 `k=30` 却命中 `k=20` 时的旧答案，
**会误以为参数没生效**——这种"沉默的错误"最难查。

**为什么 `lang` 也要进 key？**（这一条是后加的）
答案只对生成它的那个语种库成立。路由是按问题文本判定的，如果将来改了判定阈值，
同一个问题可能被路由到另一个库——不写进 key 的话就会命中另一个语料的答案，
而且 `cache_hit` 还显示 `"exact"`，完全看不出错。

## ② 向量缓存 —— 省算力

包装 `HuggingFaceEmbeddings` 的 `embed_documents` / `embed_query`，
**只把未命中的文本送进模型**：

```python
cached = cache.get_embeddings(texts, model_tag)            # 命中的直接拿
miss_texts = [t for t in texts if key(t) not in cached]    # 未命中的才算
```

### Key 里为什么必须带"模型标签"

Key 形如：

```
rag:embed:zh|./text2vec-base-chinese|seq512:9c1b...
         └────────── cache_tag ──────────┘ └─ 文本 sha256 ─┘
```

**向量是模型算出来的。** 两个不同的模型，即使输出维度相同（都是 768），
算出来的向量也分属**完全不同的向量空间**，混在一起比较得到的是噪声。

而这个标签必须覆盖**所有会改变向量取值的因素**：

| 因素 | 为什么 |
|---|---|
| 语种 | 中英用了两个不同的模型 |
| 模型路径 | 换了模型，向量就变了 |
| `max_seq_length` | 只改了截断长度，向量也会变（且**不报错**） |

**这三样少写一样，就会出现"改了配置但缓存还在返回旧向量"**——而且是静默的。

> 这里有个真实教训：项目原注释写着"文本 hash 与模型名绑定，换模型不会命中旧向量"，
> 但**代码里根本没有模型名**。注释描述的是一个从未实现的意图。见第 6 节。

### TTL 为什么比问答缓存长得多

`CACHE_EMBEDDING_TTL` 默认 86400 秒（24 小时），而问答缓存只有 1 小时。

因为**向量的有效期取决于"模型有没有变"，而不是"文档有没有变"**。
上传新文档时清掉向量缓存纯属浪费——同一段文本下次还要重算。
只有换 embedding 模型时才需要清。

这也解释了为什么 `invalidate_caches()` 里清的是 `["qa", "rerank"]`，
**故意不含 `"embed"`**。

## ③ 精排分数缓存 —— 省最慢的一环

Key 形如：

```
rag:rerank:4d7e...        # sha256(问题 + "||" + 片段)
```

**为什么 key 是 `(问题, 片段)` 组合而不是只按片段？**
因为 cross-encoder 打的分**依赖于问题**——同一段文本，对"什么是 ReAct"和
"ReAct 有什么局限"这两个问题，相关度完全不同。

用组合做 key，就能让"同一问题换文档"、"同一文档换问题"都部分复用。

**TTL**：`CACHE_RERANK_TTL`，默认 3600 秒。

> 一个值得注意的细节：精排缓存的 key **不含版本号**（只有 QA 缓存含）。
> 这意味着上传新文档后，版本号提升**无法**让精排缓存失效——
> 它只能靠 `invalidate_caches()` 里显式地 `clear(["rerank"])` 来清。
> 两者必须配套，少一个就会留下脏数据。

## 三层的 TTL 汇总

| 层 | 环境变量 | 默认 | 为什么是这个量级 |
|---|---|---|---|
| 问答 | `CACHE_ANSWER_TTL` | 3600（1 小时） | 答案对文档敏感，文档一变就该作废 |
| 向量 | `CACHE_EMBEDDING_TTL` | 86400（24 小时） | 只跟模型有关，跟文档无关 |
| 精排 | `CACHE_RERANK_TTL` | 3600（1 小时） | 分数跟问题有关，问题集不会长期不变 |

TTL 在 `.env` 里都能改，配置项读的是 `os.getenv`，改完**要重启服务**才生效
（模块导入时读一次）。

## 命中率怎么看

```bash
curl http://127.0.0.1:8000/cache/stats
```

返回里每个层都有 `{层}_hit` / `{层}_miss` / `{层}_hit_rate`。
统计是**进程内的计数器**（`cache.py:46-49`），用 `threading.Lock` 保护——
因为它要被 FastAPI 的线程池并发访问。

> 注意：统计计数器**不随 Redis 共享**。多实例部署时每个进程各算各的，
> 而缓存本身是共享的。这是刻意的取舍——为了统计去加一次 Redis 往返不值得。
