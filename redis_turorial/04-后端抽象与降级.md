# 04 后端抽象与降级

对应代码：`cache.py:76-200`

这一节讲的是**整个缓存层的架构核心**：怎么让"用 Redis"和"不用 Redis"对上层完全透明。

## 三种后端模式

配置在 `.env`：

```bash
CACHE_BACKEND=auto          # auto（默认）/ redis / memory
REDIS_URL=redis://127.0.0.1:6379/0
```

| 模式 | 行为 | 适用场景 |
|---|---|---|
| `auto`（默认） | 能连上 Redis 就用 Redis；连不上**安静降级**为进程内内存 | 开发 / 演示 |
| `redis` | 强制 Redis，连不上**直接抛错** | 生产 |
| `memory` | 只用进程内内存，零外部依赖 | 单机 / 离线调试 |

### 为什么 `auto` 要降级，而 `redis` 要报错

代码在 `cache.py:190-199`：

```python
try:
    _backend = _connect_redis()
    print(f"[cache] 已连接 Redis：{REDIS_URL}（TTL: ...）")
except Exception as e:
    if CACHE_BACKEND == "redis":
        raise RuntimeError(f"CACHE_BACKEND=redis 但连接失败：{e}") from e
    _backend = _MemoryBackend()
    print(f"[cache] Redis 不可用（{type(e).__name__}: {e}），已降级为进程内内存缓存；"
          f"问答结果仍会缓存，但重启即失效、多进程不共享。")
```

**这是整个项目里唯一一处"故意不 fail-open"的地方**，值得单独理解：

- 开发时：Redis 没起也想能跑 → 降级，而且打印一句**说明降级后果**的话
- 生产时：如果你的架构假设"多实例共享缓存"，静默降级会导致
  **每个实例各自缓存、命中率暴跌、用户看到不一致的结果**——
  这属于"配置错误应该立刻发现"，所以宁可启动就失败

> 一句经验：**静默降级适合开发环境，不适合生产环境。**
> 生产环境的降级必须"吵"——要么报错，要么至少打进监控。

### 降级后的能力边界

内存后端是**单进程**的。这意味着降级后：

| 能力 | Redis | 内存 |
|---|---|---|
| 重启后仍有效 | ✅ | ❌ |
| 多进程 / 多实例共享 | ✅ | ❌（各存各的） |
| 功能正确性 | ✅ | ✅ **不受影响** |

**最后一行是关键**：降级只影响"缓存的效果"，不影响"缓存的正确性"。
这正是铁律一（缓存是加速层）的体现。

## 双检锁单例

`cache.py:176-183`：

```python
def _get_backend():
    global _backend
    if _backend is not None:          # ① 无锁快路径
        return _backend
    with _backend_lock:
        if _backend is not None:      # ② 拿到锁后再检查一次
            return _backend
        ...                           # ③ 真正初始化
```

这叫**双检锁（double-checked locking）**。为什么要检查两次？

- **第一次（无锁）**：99.99% 的调用都走这里。已经初始化好了，直接返回，**不抢锁**。
  如果只有锁没有这层，每次读缓存都要抢一次锁，性能白白损失。
- **第二次（持锁）**：防止**两个线程同时通过了第一次检查**，
  然后各自初始化一个后端（Redisd 连接建两条 / 内存后端建两个 → 数据分裂）。

在 Python 里由于 GIL 的存在，这个问题的严重性比 C++/Java 小，但**依然存在**——
`if` 判断和赋值之间可能发生线程切换。

> 项目里这个模式出现在**四个地方**：`cache._get_backend`、
> `rag_langchain.get_embedding_model`、`rag_langchain._get_chroma_client`、
> `app.get_store / get_retriever / get_chain`。写法完全一致。

## 内存后端的三个坑

### 坑一：必须用可重入锁

```python
class _MemoryBackend:
    def __init__(self) -> None:
        self._data: Dict[str, tuple] = {}
        # 必须是可重入锁：incr() 内部会调用 self.get()，普通 Lock 会自死锁
        self._lock = threading.RLock()
```

`threading.Lock` 是**不可重入**的——同一个线程第二次 `acquire()` 会**死锁**。
而 `RLock` 允许同一线程重复获取。

> 这是个很容易踩的坑：代码平时跑得好好的，某次重构让 `get()` 在持锁状态下被调用，
> 整个服务就卡死了，而且**没有报错**（线程就那么静静地等）。

### 坑二：过期是"惰性"的

```python
def get(self, key: str) -> Optional[str]:
    with self._lock:
        item = self._data.get(key)
        if item is None:
            return None
        value, expire_at = item
        if expire_at and expire_at < time.time():   # 惰性过期
            self._data.pop(key, None)
            return None
        return value
```

**只在被读取时才检查过期**，没有后台线程去主动清理。

好处是零成本（不需要定时任务）；坏处是**如果一个 key 写过之后再也没被读过，
它会永远占着内存**。

对 Redis 来说这不是问题（Redis 有主动过期 + 内存淘汰策略），
但内存后端作为降级方案，这个简化是可以接受的——反正进程重启就清空了。

### 坑三：`incr()` 不能走 `get()`

这是最有意思的一处，注释写得很清楚（`cache.py:110-117`）：

```python
def incr(self, key: str) -> int:
    # 这里必须直接操作 _data，不能用 self.get()：
    # 虽然 RLock 可重入不会死锁，但 get() 会把过期的版本号当成 0 重新计数，
    # 导致版本号回退（回退 = 命中已被作废的旧缓存）。
    with self._lock:
        current = int(self._data.get(key, ("0", 0))[0]) + 1
        self._data[key] = (str(current), 0)     # 版本号不设过期
        return current
```

两个要点：

1. **版本号 key 不设过期**（`expire_at = 0` 表示永不过期）。
   如果版本号过期了，下次 `incr` 会从 0 重新开始 → **版本号回退** →
   用旧版本号算出的 key 又"复活"了 → **命中本该作废的旧答案**。
   这是"缓存让答案变错"的典型事故。

2. **不能用 `get()`**，因为 `get()` 会把过期的 key 当作不存在，返回 `None`，
   于是 `int(None or "0")` = 0，同样导致回退。

> Redis 侧的 `INCR` 是原生的原子操作，服务端保证不会出现这种问题。
> 但在**自己实现的后端里，必须显式地保证同样的语义**——
> 这就是"抽象泄漏"：接口一样，语义要自己扛。

## 测试钩子：替换客户端实现

`cache.py:154-173`：

```python
def _connect_redis():
    module_name = os.getenv("RESP_CLIENT_MODULE", "redis")
    module = __import__(module_name, fromlist=["from_url"])
    ...
```

**默认用官方的 `redis` 包**；如果设了环境变量 `RESP_CLIENT_MODULE`，
就改用那个模块的 `from_url()`。

这是给"没装 redis 包但要验证 Redis 代码路径"准备的——配合第 3 节那两个
手写实现使用。**生产环境不要设置它**（注释里明确写了）。

```python
    try:
        client = module.from_url(REDIS_URL, protocol=2, **kwargs)
    except TypeError:
        # 极简 RESP 客户端没有 protocol 参数，退回原调用方式
        client = module.from_url(REDIS_URL, **kwargs)
```

这个 `try/except TypeError` 是在兼容自写的 `RespClient`——它没有 `protocol` 参数。

### 为什么要强制 `protocol=2`

```python
# 强制走 RESP2：redis-py 5+ 默认用 RESP3 并在连接时发送 HELLO，
# 而 Redis 6 以下（含 Windows 版 redis 5.0.x）不认识 HELLO，
# 会直接抛 ResponseError: unknown command `HELLO`，导致整个 Redis 后端失效。
```

RESP3 是 Redis 6 引入的新协议版本。redis-py 5+ 默认尝试 RESP3，
连接时会先发 `HELLO` 命令协商版本——**老 Redis 不认识 `HELLO`，直接报错**。

Windows 上的 Redis 长期停留在 5.0.x（微软的移植版），所以这个坑在 Windows 上必踩。
加 `protocol=2` 强制走旧协议就解决了。

> 教训：**客户端库升级可能悄悄改变协议行为**，而服务端跟不上就会整个失效。
> 这类问题在本地开发时不一定暴露（你本机可能是新版 Redis），一到别的环境就炸。

## 连接超时为什么只有 1 秒

```python
kwargs = dict(decode_responses=True, socket_connect_timeout=1, socket_timeout=1)
```

**缓存是加速层，不该拖慢主流程。** 如果 Redis 网络抖动，等 30 秒才降级，
用户已经等不起了。1 秒连不上就干脆放弃、走真实计算——
宁可慢一点（真实计算），也不要卡住（等缓存超时）。
