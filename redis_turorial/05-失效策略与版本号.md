# 05 失效策略与版本号

对应代码：`cache.py:216-268`、`cache.py:344-363`、`rag_langchain.py` 的 `invalidate_caches()`

这一节解决的是缓存里**最难、也最容易出错**的问题：**怎么让旧数据失效。**

## 问题：文档更新了，答案还是旧的

设想这个场景：

1. 用户上传了文档 A，问了"这篇论文的主要贡献是什么"，答案被缓存
2. 用户上传了文档 B（知识库变了）
3. 用户再问同样的问题

如果缓存没失效，他会拿到**基于文档 A 的答案**——而且**看起来完全正常**。
用户无法察觉自己在读错误信息。这是缓存系统最典型的事故。

## 方案一：TTL（兜底，不是解法）

每条记录都带过期时间，`SET` 时指定：

```python
def set(self, key: str, value: str, ttl: int) -> None:
    self._client.set(key, value, ex=ttl or None)      # Redis 后端
```

对应网线上的命令是 `SET key value EX 3600`。

**TTL 只能兜底，不能解决问题。** 因为：

- TTL 太长 → 文档更新后，用户要等最长 TTL 时间才能拿到新答案
- TTL 太短 → 缓存命中率暴跌，等于白做

**失效必须由"事件"驱动，不能只靠时间。** 事件就是"知识库变了"。

## 方案二：逐个删 key（看起来直观，实际不可靠）

最直接的想法：文档更新时，把所有相关的 key 删掉。

**问题是"所有相关的 key"你根本列不全**：

- QA 缓存的 key 是 `sha256(问题 + 参数)`，**你无法从 key 反推出哪些问题被问过**
- 更别说 embedding 缓存（按文本 hash）和 rerank 缓存（按问题+片段 hash）

想删干净，只能**遍历整个 keyspace** 去匹配。这既慢又容易漏。

## 方案三：版本号（本项目的做法）

**核心思路：不去删旧 key，而是让新旧 key 变得不一样。**

```python
def make_key(kind: str, *parts: str) -> str:
    """key 格式：rag:v{版本}:{类型}:{内容hash}。带版本号，便于整体失效。"""
    raw = "||".join(parts)
    digest = hashlib.sha256(raw.encode("utf-8")).hexdigest()[:32]
    return f"rag:v{get_version()}:{kind}:{digest}"
```

注意 key 里的 `v{版本}`：

```
rag:v1:qa:8f2a...      ← 文档更新前算出的 key
rag:v2:qa:8f2a...      ← 文档更新后算出的 key（版本号变了）
```

**一次 `INCR` 就让所有旧 key 失效**——不是删掉它们，而是**再也拼不出那个 key 了**。

```python
def bump_version() -> int:
    version = _get_backend().incr(VERSION_KEY)
    print(f"[cache] 知识库已变更，缓存版本提升到 v{version}，旧缓存全部失效")
    return version
```

### 为什么用 `INCR` 而不是"读出来 +1 再写回去"

```python
def incr(self, key: str) -> int:
    return int(self._client.incr(key))       # Redis 原生命令
```

因为 `INCR` 是**原子操作**，由 Redis 服务端保证。

如果用"读-改-写"：

```python
v = client.get(VERSION_KEY)      # 进程 A 读到 1
# ← 就在这一瞬间，进程 B 也读到 1，也 +1 写回 2
client.set(VERSION_KEY, v + 1)   # 进程 A 也写 2
```

**两个并发上传，版本号只涨了 1。** 版本号涨少了本身不会出错（少失效一次而已），
但如果出现"两个请求都基于旧值覆盖"，就可能**版本号回退**——那才是灾难。

用 `INCR` 就没有这个问题，服务端串行化保证了结果一定正确。

### 版本号 key 绝对不能过期

```python
VERSION_KEY = "rag:cache_version"
```

这个 key 是**唯一一个不设 TTL 的 key**。

如果它过期了 → 下次 `incr` 从 0 开始 → **版本号回退** →
之前"用 v5 算出的 key"和现在"用 v1 算出的 key"…… 等等，这里要仔细想：

版本号回退到 1，而可能有历史的 `rag:v1:qa:xxx` 还躺在 Redis 里没被清
（TTL 还没到）→ **那些本该作废的旧 key 又变得"可命中"了**。

内存后端里这一条写得更明确（`cache.py:110-117`，见第 4 节）。

## 清理：删掉所有历史版本

版本号让旧 key **失效**，但它们仍占着 Redis 内存。需要定期清掉：

```python
def clear(kinds: Optional[List[str]] = None) -> int:
    kinds = kinds or ["qa", "embed", "rerank"]
    prefixes = {"qa": "rag:v*:qa:",              # ← 注意这个 *
                "embed": "rag:embed:",
                "rerank": "rag:rerank:"}
    for kind in kinds:
        deleted += _get_backend().delete_prefix(prefixes[kind])
```

**QA 的前缀故意写成 `rag:v*:qa:`**——那个 `*` 是关键：

- 如果写 `rag:v{当前版本}:qa:`，只能清掉当前版本的 key，
  **所有历史版本的 key 会变成永远删不掉的垃圾**
- 写 `rag:v*:qa:` 则一次清掉所有版本

注释里写得很直白（`cache.py:345-350`）：

> QA 前缀故意用 glob `rag:v*:qa:` 以便清掉**所有历史版本**，避免旧 key 变成删不掉的垃圾。

### 前缀扫描为什么要用 `SCAN`

```python
def delete_prefix(self, prefix: str) -> int:
    """用 SCAN 删除，绝不用 KEYS（KEYS 会阻塞整个 Redis 实例）。"""
    deleted = 0
    for key in self._client.scan_iter(match=f"{prefix}*", count=500):
        deleted += self._client.delete(key)
    return deleted
```

这是**生产环境最重要的 Redis 常识之一**，第 6 节详细讲。

## `bump_version` 什么时候被调用

在 `rag_langchain.invalidate_caches()`：

```python
def invalidate_caches() -> int:
    for sc in _semantic_caches.values():
        sc.clear()                              # ① 语义缓存（内存对象，直接清）
    deleted = cache.clear(["qa", "rerank"])     # ② 问答 + 精排：物理删除
    cache.bump_version()                        # ③ 版本号 +1：逻辑失效
    return deleted
```

调用方是 `app.py` 的 `/upload`——**上传新文档之后**。

注意三件事**同时做**：

| 动作 | 作用 |
|---|---|
| `_semantic_caches.clear()` | 语义缓存是进程内对象，直接清空 |
| `cache.clear(["qa","rerank"])` | 物理删除，释放 Redis 内存 |
| `bump_version()` | 逻辑失效，防止"漏删" |

**为什么三个都要做？** 因为防护要冗余：

- 只 bump 不 clear → 旧 key 堆积成垃圾
- 只 clear 不 bump → 万一 clear 漏了（如新增了一种缓存类型忘了加进前缀表），
  旧 key 就会被命中
- **两个都做**：bump 保证了正确性（即使 clear 漏了也命不中），
  clear 保证了内存不浪费

**注意 `clear()` 里故意不含 `"embed"`**——向量只跟模型有关，跟文档无关，
清了纯属浪费（见第 2 节）。

## 一个真实项目里的取舍：全局版本号

本项目现在是**中英双库**，但版本号是**全局唯一**的一个：

```python
VERSION_KEY = "rag:cache_version"
```

所以**上传一份中文文档，会让英文的问答缓存也一起失效**。

这是**刻意**选的：

| 方案 | 后果 |
|---|---|
| 全局版本号（现在） | 多失效 → 英文缓存被误清 → **只是变慢** |
| 每语种一个版本号 | 精确失效 → 但多一处状态、多一处可能出错的地方 |

**判断标准是"错了会怎样"**：

- 多失效 → 用户多等几秒，**答案仍然正确**
- 少失效 → 用户拿到旧文档的答案，**答案错误且无法察觉**

在缓存里，**永远优先选"宁可多失效"**。
