## 实验一：不装任何东西，手撸 RESP

这个实验的目的是**亲眼看见协议**。用一个最原始的 socket，自己拼字节、自己读回复。

```bash
$PY - <<'PYEOF'
import socket

s = socket.create_connection(("127.0.0.1", 6379), timeout=3)

def cmd(*args):
    """自己拼 RESP 数组格式的命令"""
    out = b"*" + str(len(args)).encode() + b"\r\n"
    for a in args:
        b = a.encode()
        out += b"$" + str(len(b)).encode() + b"\r\n" + b + b"\r\n"
    s.sendall(out)
    return s.recv(4096)          # 简单起见，一次读一坨

print("PING      ->", cmd("PING"))
print("SET       ->", cmd("SET", "rag:tutorial:demo", "hello"))
print("GET       ->", cmd("GET", "rag:tutorial:demo"))
print("GET 不存在 ->", cmd("GET", "rag:tutorial:nosuchkey"))   # 注意是 $-1
print("INCR      ->", cmd("INCR", "rag:tutorial:counter"))
print("INCR      ->", cmd("INCR", "rag:tutorial:counter"))
print("SET 带 EX ->", cmd("SET", "rag:tutorial:ttl", "x", "EX", "100"))
print("TTL       ->", cmd("TTL", "rag:tutorial:ttl"))
print("DEL       ->", cmd("DEL", "rag:tutorial:demo"))
print("DELETE    ->", cmd("DELETE", "rag:tutorial:demo"))       # ← 看看这个

s.close()
PYEOF
```

**重点观察两件事**：

1. `GET 不存在` 返回的是 `$-1`，**不是**空字符串 `$0`
2. 最后一条 `DELETE` 会返回 `-ERR unknown command` ——
   **这就是第 6 节讲的 Bug 1**。真实 Redis 只认 `DEL`。

> 如果 Redis 没启动（连接被拒绝），先跳到实验二启动它。

**清理**：

```bash
redis-cli DEL rag:tutorial:ttl rag:tutorial:counter
```

## 实验二：启动真实 Redis，观察 key

### 启动

```bash
redis-server
```

（保持这个终端开着。Windows 版会打印一个 ASCII 艺术字的 Redis logo。）

### 另开一个终端，观察

```bash
redis-cli PING                       # PONG
redis-cli DBSIZE                     # 当前库里有多少 key
redis-cli KEYS 'rag:*'               # 看项目写入的 key（学习用；生产别这么干）
```

### 让项目写点缓存进去

启动服务，然后提几个问题（需要有 DeepSeek Key 才能走完整链路，但缓存会在那之前就写入）：

```bash
# 终端 A
redis-server

# 终端 B
cd /d/Project/RAG
CACHE_BACKEND=redis $PY -c "
import cache
cache.set_answer('测试问题', 5, 20, '测试答案', ['片段1'])
cache.set_embeddings([('一段文本', [0.1, 0.2])], 'zh|demo')
cache.bump_version()
print('版本号 =', cache.get_version())
"
```

然后**用 redis-cli 看真实写进去的东西**：

```bash
redis-cli KEYS 'rag:*'
redis-cli GET "rag:cache_version"           # 版本号（不过期）
redis-cli TTL "rag:cache_version"           # -1 表示永不过期 ← 第 5 节讲的
redis-cli KEYS 'rag:v*:qa:*'                # QA 缓存，key 里带版本号
redis-cli GET "rag:v1:qa:..."               # 把上面查到的 key 填进来，看 value 是 JSON
```

**观察 TTL 的差别**：

```bash
redis-cli KEYS 'rag:*' | while read k; do echo "$(redis-cli TTL "$k")  $k"; done
```

你会看到版本号是 `-1`（永不过期），而其他 key 有正数 TTL。

**清理**：

```bash
redis-cli --scan --pattern 'rag:*' | xargs redis-cli DEL
```

> 注意这里用了 `--scan` 而不是 `KEYS`——`redis-cli` 的 `--scan` 内部就是 `SCAN`。
> 这就是生产环境清理 key 的正确姿势（第 6 节）。

## 实验三：零依赖验证 Redis 代码路径

这个实验**不需要真实 Redis**，用的是项目自带的那两个手写实现。

**终端 A** —— 启动 mini 服务端：

```bash
cd /d/Project/RAG
$PY tools/mini_redis_resp.py 6399
# [mini-redis] listening on 127.0.0.1:6399
```

**终端 B** —— 让 `cache.py` 走这条路径：

```bash
cd /d/Project/RAG
CACHE_BACKEND=redis \
REDIS_URL=redis://127.0.0.1:6399/0 \
RESP_CLIENT_MODULE=tools.resp_client \
$PY verify_cache.py
```

应该看到 `通过 35/35`。

**关键**：这次跑的是 `cache.py` 里**生产用的 `_RedisBackend` 代码**，
只有"对端"是替身。这就是第 3 节说的"替换环境，不替换被测代码"。

**然后看它到底发了什么命令**：在终端 A 按 `Ctrl+C` 停止，
会在当前目录生成 `mini_redis_commands.log`：

```bash
cat mini_redis_commands.log | sort | uniq -c | sort -rn | head -20
```

你会看到命令的统计分布。**找找里面有没有 `KEYS`**——
按设计它不应该出现（应该全是 `SCAN`）。

## 实验四：亲手验证三个 bug

### Bug 1：`DELETE` vs `DEL`

```bash
redis-cli DEL rag:tutorial:x            # 真实 Redis：正常
redis-cli DELETE rag:tutorial:x         # 真实 Redis：报错

$PY -c "
from tools.resp_client import RespClient
c = RespClient('127.0.0.1', 6399)       # 指向 mini 服务端
print('mini 服务端认 DELETE:', c.delete('k'))
"
```

**结论**：项目客户端 + mini 服务端 = 能跑；项目客户端 + 真实 Redis = 挂。
两个错误互相印证，成了一对"正确"。

### Bug 2：注释与实现不一致

```bash
grep -n "与模型名绑定" cache.py
```

去看看那行注释下面的代码到底拼没拼模型名。（现在已修复，你会看到
`_embed_storage_key` 里确实有 `model_tag`。）

### Bug 3：死代码里的错误

```bash
grep -n "SEMANTIC_CACHE" .env
```

`.env` 里 `SEMANTIC_CACHE=0`。把它改成 `1`，启动服务，问一个问题——
在修复前这会直接 `TypeError`。（现在已修复。）

**把这个开关改回去。**

## 练习题

按难度排序。**前两题直接对应第 6 节讲的真实问题。**

### 练习 1（简单）：修掉 Bug 1

把 `tools/resp_client.py` 和 `tools/mini_redis_resp.py` 里的 `DELETE` 都改成 `DEL`，
然后**用真实的 Redis 重跑实验三**，确认能通。

> 这题的价值不在改代码，而在**验证**：改完之后，
> 你要能说清楚"为什么之前测不出来"。

### 练习 2（中等）：给向量缓存加 MGET

把 `cache.py` 的 `get_embeddings` 从 N 次 `GET` 改成一次 `MGET`
（需要在 `_RedisBackend` 和 `RespClient` 里各加一个 `mget`，
mini 服务端也要加 `MGET` 的处理）。

完成标准：用 `mini_redis_commands.log` 确认，查 100 个文本只产生 **1 条** `MGET`。

### 练习 3（中等）：给 TTL 加随机抖动

第 6 节讲了"缓存雪崩"。把 `ANSWER_TTL` 改成一个范围，
每次写入时随机取一个值（如 `3600 ± 300`）。

完成标准：连续写 20 条，用 `redis-cli TTL` 观察，TTL 不应该完全相同。

### 练习 4（较难）：实现 `SETNX` 防击穿

第 6 节讲了"缓存击穿"：热 key 过期的瞬间，大量并发请求会一起打到后端。

用 `SETNX`（SET if Not eXists）实现一个简单的互斥锁：
只让第一个请求去真实计算，其余请求短暂等待后重试读缓存。

完成标准：并发发起 10 个相同问题，确认只有 1 次真实计算
（看 `cache.get_stats()` 的 `qa_miss` 是否只涨了 1）。

> `SETNX` + 过期时间要一步完成，正确写法是
> `SET key value NX EX 10`——**不要**分成 `SETNX` + `EXPIRE` 两步，
> 中间挂掉就会留下一个永远不释放的锁。

### 练习 5（开放）：观察真实命中率

跑一批真实问题（走完整链路，需要 DeepSeek Key），然后：

```bash
curl http://127.0.0.1:8000/cache/stats
```

看三层缓存各自的命中率，**想想哪一层的收益最大、为什么**。

提示：结合第 1 节的成本表——哪一层的"单位收益"最高？

## 学习路线的终点

如果你把上面六节都读懂了，并且做完前两题，你就掌握了：

- ✅ RESP 协议（能自己读写它）
- ✅ 缓存的三种失效策略（TTL / 删除 / 版本号）及各自的适用场景
- ✅ 生产环境的四条硬规则（SCAN / 原子操作 / 协议版本 / 避免 N+1）
- ✅ 降级设计（fail-open vs fail-closed 的取舍）
- ✅ 并发下的单例与原子性

剩下的就是实践了。**最值得养成的习惯是**：

> 看到一个"看起来没问题"的实现时，问一句
> **"它在什么情况下会不成立？"** ——
> 这三个 bug 全都藏在这个问题的答案里。
